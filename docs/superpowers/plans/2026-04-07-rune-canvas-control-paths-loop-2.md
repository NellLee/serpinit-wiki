# Rune Canvas Control Paths Loop 2 Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents are both available and allowed for this turn) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make control and relationship paths the primary readable layer in the `/dev/runes` canvas so complex runes communicate more of their control chain directly in the image.

**Architecture:** Keep the current inspector layout and rune document model intact while upgrading the canvas reading language. Push more meaning into the relation geometry and relation styling generated by `runePresentation.ts`, then let `RuneCanvas.svelte` render those stronger distinctions with clearer drawing order and visual emphasis. Use the existing `/dev/runes` Playwright coverage plus presentation tests to guard both path semantics and rendered behavior.

**Tech Stack:** SvelteKit, Svelte SVG rendering, TypeScript, existing rune presentation pipeline, Vitest, Playwright, existing Yarn workflow

---

- [ ] **Step 1: Write the failing presentation-path test**

Extend `app/src/lib/components/runes/runePresentation.test.ts` so it asserts the relation modes now produce more strongly differentiated geometry than the current minor-variant line language.

The test should cover at least:
- `strahl` remains a direct path class
- `bogen` follows a visibly shell-bound arc
- `strahlbogen` has a mixed redirection path distinct from both
- `bruecke` remains a transverse coupling path, not just another arc

Example expectation shape:

```ts
test('derives relation geometry with distinct control-path classes', () => {

  expect(presentation.relationsByMode.bogen?.path).toContain('A');
  expect(presentation.relationsByMode.strahlbogen?.path).toMatch(/L .* A .* L/);
  expect(presentation.relationsByMode.bruecke?.path).toContain('Q');
});
```
